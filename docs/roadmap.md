# air 项目后续演进路线图

> 本文档是 air 后续三阶段更新的执行依据。按下列阶段顺序推进，不要跳级。
> 修改相关链路时同步更新本文档与对应 `.codex/*.md` 流程文档；源码与文档不一致时以源码为准，并在本文档补齐差异。

## 总体优先级

**阶段一（完善核心 UX）→ 阶段二（全平台）→ 阶段三（多内核）**

核心理由：先在主平台（Windows）把日常可用性功能打磨成型，让产品设计与抽象边界稳定下来，再把成型的实现移植到其它平台；多内核是最大架构改动，必须等单内核产品成熟、用户反馈充分后再按真实需求驱动抽象，避免过度设计。

---

## 阶段一：完善核心 UX（首页 + 系统代理 / TUN 托盘开关）

### 目标

在 Windows 主平台上补齐 Clash 类管理器的基线功能，让用户安装后无需手动改系统设置即可完成日常使用闭环。

### 范围

1. **系统代理开关**
   - 一键启用/禁用 Windows 系统代理（HTTP/HTTPS），指向 mihomo mixed-port。
   - 状态回填：读取当前系统代理状态，UI 同步显示。
   - 退出应用或停止内核时按配置策略还原系统代理（避免遗留脏代理导致断网）。

2. **TUN 虚拟网卡开关**
   - 一键启用/禁用 TUN 模式，通过 `platform::core_service` 托管提权核心进程，不在 UI 回调里直接调 Win32 API。
   - TUN 开关需校验内核服务状态、权限来源，失败给出脱敏诊断。
   - 与系统代理互斥/共存策略要明确（通常 TUN 启用时不依赖系统代理）。

3. **托盘右键菜单**
   - 菜单项：显示主窗口、启用/禁用系统代理、启用/禁用 TUN、退出。
   - 菜单状态与主窗口、内核生命周期、代理/TUN 状态实时同步。
   - 复用已有托盘事件链路，不新开并行通知入口。

4. **首页（仪表盘）补齐**
   - 聚合：内核运行状态、系统代理/TUN 当前状态、运行时配置概要、日志/流量/内存监控。
   - 首页作为状态总入口，系统代理/TUN 开关既在托盘也在首页/状态栏可达。

### 架构纪律（必须守住）

- 系统代理、TUN、托盘菜单开关逻辑必须放进 `air-platform`，通过 trait 抽象，业务层只调抽象接口。
- 禁止在 UI 回调或 `air-ui` 内直接散落 `cfg(target_os)` 或 Win32 调用。
- 权限相关操作（TUN、服务安装/启停）走 `platform::core_service` 或 `platform::elevated_process`。
- 所有状态变更走 app command router / 事件总线，UI 只展示和收集输入。
- 涉及端口、地址、secret 的日志必须脱敏。

### 落地路径建议

1. 在 `air-platform` 抽象 `SystemProxyControl` / `TunControl` trait，Windows 先实现，其它平台留 `unsupported` 占位（为阶段二预留）。
2. 在 app 层接入开关命令，command router 覆盖成功/失败/取消/核心未运行路径并验证错误脱敏。
3. 托盘菜单复用现有托盘事件链路，菜单项状态由 app snapshot 驱动。
4. 首页状态从 app snapshot、配置仓储、mihomo 事件构造，不依赖 fake 数据。

### 完成判据

- Windows 下可一键启用/禁用系统代理并正确回填状态；退出/停止内核时按策略还原。
- TUN 开关可用，权限不足/服务未就绪时给出脱敏诊断。
- 托盘右键菜单功能完整且状态与主窗口一致。
- 所有新增命令有成功/失败/取消/核心未运行测试。
- 平台逻辑全部隔离在 `air-platform`，业务层无 `cfg(target_os)`。

## 阶段二：全平台（macOS / Linux）

### 目标

把阶段一成型的功能按 macOS、Linux 的平台模型补齐，保持架构隔离不变。

### 范围

1. **系统代理**
   - macOS：`networksetup`。
   - Linux：NetworkManager / pkexec（需处理发行版差异与无图形权限场景的降级）。

2. **TUN 权限与服务化**
   - macOS：权限与 launchd 托管。
   - Linux：capabilities / systemd / pkexec 提权路径。

3. **托盘 / 自启 / 通知**
   - 各平台托盘事件、开机自启、系统通知补齐。
   - 当前 macOS/Linux 的 TUN 权限、自启、托盘、通知、服务化、打包发布仍为降级或 unsupported，本阶段逐项补齐。

4. **打包发布**
   - 三平台安装包/分发格式补齐。

### 架构纪律

- 阶段一建立的 `SystemProxyControl` / `TunControl` trait 保持不变，只补平台实现。
- 任何新增平台差异继续走 `air-platform`，不允许业务层出现 `cfg(target_os)`。
- 平台实现失败必须降级为明确诊断，不能静默断功能。

### 完成判据

- 三平台系统代理/TUN/托盘/自启/通知功能可用或给出明确降级诊断。
- 业务层零 `cfg(target_os)`。
- 打包发布流程覆盖三平台。

## 阶段三：多内核支持

### 目标

在 mihomo 单内核产品成熟、用户反馈充分后，抽象核心层以支持 sing-box / xray / v2ray 等内核。

### 范围

1. **核心抽象层**
   - 配置模型差异（各内核 YAML/JSON schema 不同）。
   - API 差异（external-controller 协议、端点、字段）。
   - 进程生命周期差异（启动参数、健康检查、重载机制）。
   - 能力差异（TUN、规则、协议支持矩阵）。

2. **按真实需求驱动抽象**
   - 至少 2 个真实内核实现后再固化抽象，避免单一样本过度设计。

### 风险

- 这是重构级工作量，`air-mihomo` / `air-config` / 进程管理深度耦合 mihomo 语义。
- 必须在阶段一、二稳定后再启动，否则容易做出"四不像"抽象层。

### 完成判据

- 核心层抽象稳定，至少支持 mihomo + 1 个其它内核。
- 抽象层有跨内核能力矩阵文档，能力差异显式表达。
- 不破坏现有 mihomo 主路径行为。

---

## 跨阶段通用约束

- 所有新增 Rust 代码包含具体中文注释，解释设计意图与边界条件。
- 配置解析保留未知字段；文件写入优先用 `FileStore` 原子写入与备份。
- 敏感信息（密钥、订阅 URL、认证头、代理密码、本地敏感路径）日志/通知必须脱敏。
- GUI 层只做展示与输入收集，业务逻辑放在 app/mihomo/storage/platform。
- 清理 fake 数据时不删测试夹具，改名为 `fake_for_test` / `sample_for_test` 或限定 `#[cfg(test)]`。
- 所有关键流程必须有详细日志。
